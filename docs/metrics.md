# 指标口径

指标定义不清楚，数字就没有意义。「格式遵循率 91%」这句话，如果不先说明「什么算合法」「分母是什么」，它可以指至少四种不同的东西。这份文档把每个指标的口径钉死。

## 一、格式遵循率（主指标）

```
格式遵循率 = 能解析成合法 AuditResult 的样本数 / 全部样本数
```

**「合法」的定义**（按顺序，全部满足才算）：

1. 输出中能提取出一段 JSON
2. JSON 语法正确
3. 能被 `AuditResult` 校验通过，即：
   - 四个字段 `conclusion` / `risk_level` / `issues` / `suggestion` 全部存在
   - `conclusion` ∈ {通过, 需修改, 不通过}
   - `risk_level` ∈ {低, 中, 高}
   - `issues` 是数组，每项含 `type` / `detail` / `severity` 且枚举值合法
   - **不允许出现未定义的字段**（pydantic 配了 `extra="forbid"`）

最后一条是刻意加严的。审核系统的入库逻辑是按字段名映射的，多出来的字段要么被静默丢弃（丢信息），要么让整个解析失败（线上事故）。宁可在这里严格。

**为什么这是主指标：** 下游是数据库。格式不合法 = 这条记录进不去，后面的人工复核队列也拿不到东西。此时审核判断对不对根本不重要——**准确率再高，进不了库就是零**。

## 二、裸 JSON 率（诊断指标）

```
裸 JSON 率 = 未经提取、直接就是合法 JSON 的样本数 / 全部样本数
```

`schema.parse_audit_output()` 有三级容错：裸 JSON → 剥代码块围栏 → 截花括号。只要走到第 2、3 级，`extracted=True`。

**为什么单独看这个：** 格式遵循率会被后处理「救」回来。

举例：模型每次都输出 ` ```json ... ``` `，靠第 2 级剥围栏全部达标，格式遵循率 100%。看起来完美，但换个解析器（比如接入方自己写的、不做围栏处理的），立刻掉到 0%。**这个模型并没有学会输出规范格式，它学会了输出一种「我们的解析器能处理」的格式。**

两个数字一起看才有意义：

| 格式遵循率 | 裸 JSON 率 | 解读 |
|---|---|---|
| 高 | 接近格式遵循率 | 真的学会了，格式稳定 |
| 高 | 明显低于格式遵循率 | 靠容错提取救回来的，有风险 |
| 低 | 低 | 没学会，需要继续训练 |

## 三、字段准确率

```
审核结论准确率 = conclusion 与金标准一致的样本数 / 全部样本数
风险等级准确率 = risk_level 与金标准一致的样本数 / 全部样本数
```

**分母是全量样本，格式失败的样本一律记为错。**

这一点必须强调，因为很容易搞错：如果只在「格式合法的子集」上算准确率，会出现**「格式越差、字段准确率越高」**的假象——因为模型往往只对简单样本输出了合法 JSON，在那批简单样本上它自然判得更准。这样的数字是自欺欺人。

分母是全量，含义就变成：「这条题从进系统到入库，端到端拿到正确结论的概率」。这才是审核系统真正关心的事。

**问题类型的 P / R / F1**（多标签，一个样本可能有多个问题类型）：

```
TP = 预测的问题类型 ∩ 金标准问题类型
FP = 预测的问题类型 - 金标准问题类型
FN = 金标准问题类型 - 预测的问题类型
精确率 P = TP / (TP + FP)
召回率 R = TP / (TP + FN)
F1 = 2PR / (P + R)
```

只比类型集合，不比 `detail` 的具体措辞。原因：`detail` 是自然语言，语义相同但表述不同的情况太多，用字符串匹配会严重低估；用模型来评判（LLM-as-judge）又会引入新的不确定性。所以只评类型，措辞留给人工抽查。

## 四、评测协议

- **测试集**：`data/test.jsonl`，300 条，与训练集的底题**完全不相交**（见 `data/STATS.md` 的隔离表）
- **解码**：贪心（`do_sample=False`）。评测必须可复现——同一份权重跑两次结果必须完全一致，否则「从 55% 提升到 91%」这种结论没有意义
- **对比**：基座模型与微调模型**跑同一份测试集、同一个 prompt、同一套解析器**
- **同一台机器**：两个模型在同一台机器、同一精度下评测。跨机器比数字没有意义

## 五、本项目指标的适用边界

**这些数字不能外推到真实题目。** 理由：

1. **测试集是合成的。** 题目由 22 个模板生成，语言复杂度远低于真实命题。真实题目有图表、有跨学科情境、有更长的题干，模型面对的是完全不同的分布。
2. **缺陷是注入的，不是自然产生的。** 真实命题的错误更隐蔽、更复杂，不像「把限定词删掉」这么规整。
3. **标签来自构造过程。** 好处是绝对可靠，代价是它只覆盖了我们**想得到**的缺陷类型。真实题库里一定有我们的分类体系没考虑到的问题——那些在测试集里根本不存在，也就不会被计入任何指标。

**正确的解读方式**：这些数字说明的是「**流水线是否跑通、微调是否让模型更倾向输出规范格式**」，而不是「这个模型能替代人工审核」。后者需要真实标注数据才能评估。

README 的 Roadmap 里把「接入真实题库并重新评测」列为未完成事项，就是这个原因。
